# Detect and handle length-truncated AI responses in run_with_tools

`run_with_tools`'s request payload (`{"model": ..., "messages": ...,
"tools": ...}`, built in `_post_chat_completion`) never sets `max_tokens`,
so the output-length ceiling for every completion is whatever each
provider defaults to implicitly — not something this pipeline controls
or even knows. Worse, the response is never checked for `finish_reason`:
`run_with_tools` treats any response with no `tool_calls` as a complete
final answer, with no way to distinguish a deliberate, finished response
from one cut off mid-generation by a length limit. Observed in practice:
a Tester step (Copilot, `claude-sonnet-4.6`) produced a response that
trailed off mid-sentence ("...let me re-read that section." and nothing
further, having made only ~7 tool calls — nowhere near
`MAX_TURNS_PER_STEP`'s 40-turn ceiling), which the pipeline silently
accepted as "Tester wrote no test files for this criterion" rather than
recognizing the response as truncated.

## Acceptance Criteria

- [ ] `_post_chat_completion`'s request payload (`src/ticket_pipeline/lib/ai_client.py`) includes an explicit `max_tokens` value, so every completion request has a known, deliberate output-length ceiling instead of relying on each provider's own implicit default.
- [ ] `run_with_tools` inspects the response's `finish_reason` before treating a `tool_calls`-free response as a final answer, rather than unconditionally returning `AIResult(text=message.get("content") or "")` whenever `tool_calls` is absent.
- [ ] A response with no `tool_calls` and `finish_reason == "length"` causes `run_with_tools` to raise a distinct `AIError` instead of returning it as a completed `AIResult`, so it flows through `run_ai_step_with_retry`'s existing retry-with-backoff mechanism the same way a transient HTTP error already does.
- [ ] A test demonstrates that a mocked response with no `tool_calls` and `finish_reason: "length"` triggers the new error path, and that a normal `finish_reason: "stop"` response with no `tool_calls` is still returned as a completed `AIResult` unaffected by this change.

### Context

**Where this was observed:** a `test-criterion` step (via the Copilot
provider, model `copilot:claude-sonnet-4.6`) against
`adhoc-ticket-snapshot-carryforward`'s third criterion. The Tester's
response ended mid-thought after ~7 tool calls (3 `list_dir`, 4
`read_file`), which is nowhere near `MAX_TURNS_PER_STEP` (40) — ruling
out the turn-count ceiling as the cause. The pipeline's own
`_handle_no_test_written` path then reported "Tester wrote no test files
for this criterion," when the actual issue was a truncated response, not
a deliberate "nothing to test" conclusion. (Separately confirmed in this
same investigation: the Tester's cut-off reasoning was in the middle of
correctly identifying a real, pre-existing `IndentationError` in
`tests/test_ticket_snapshot.py` — its instinct was right, it just ran out
of room before finishing or acting on it.)

**Exact current mechanism (`src/ticket_pipeline/lib/ai_client.py`):**
```python
parsed = _post_chat_completion(
    {"model": model, "messages": messages, "tools": tools}, label
)
...
message = parsed["choices"][0]["message"]
messages.append(message)
tool_calls = message.get("tool_calls")
if not tool_calls:
    return AIResult(text=message.get("content") or "")
```
No `max_tokens` key anywhere in the payload. No read of
`parsed["choices"][0].get("finish_reason")` anywhere in this function,
`_post_chat_completion`, or `run_prompt` (`run_prompt` shares
`_post_chat_completion` and has the identical gap, though it currently
has no callers in the codebase — fixing this at the shared
`_post_chat_completion`/`run_with_tools` layer covers it for free if it's
ever used).

**Why this isn't `MAX_TURNS_PER_STEP`:** that ceiling
(`src/ticket_pipeline/lib/ai_client.py`, `MAX_TURNS_PER_STEP = 40`)
bounds the number of tool-call round-trips in one `run_with_tools`
session — it exists for a model that's confused and looping tool calls
without concluding, and raises `StepBucketExceeded` when exceeded, which
would show up as a distinct, loud error, not a silently-accepted
truncated answer. The observed incident used a small fraction of that
budget, so raising it would not have prevented or even affected this
failure mode.

**Why raising a distinct `AIError` is the right integration point, not a
new continuation/retry mechanism:** `run_ai_step_with_retry`
(`src/ticket_pipeline/lib/pipeline_lib.py` ~507) already retries any
`AIError` from a fresh `run_with_tools` call (new message history each
attempt, exponential backoff) — the same mechanism that already absorbs
transient HTTP 500s. A length-truncated response raising `AIError` gets
this retry behavior for free, without inventing a separate
continue-the-previous-response code path.

**Explicitly not required by this ticket:** a "continue this specific
truncated response" mechanism (feeding the partial content back and
asking the model to finish it) — a fresh retry via the existing
mechanism above is sufficient and much simpler; a continuation mechanism
can be considered separately later if fresh retries turn out to be
insufficient in practice.
